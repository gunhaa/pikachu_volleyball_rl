## 여기서 남은 것 — 이후 Phase 가 기대도 되는 것

  `(baseSeed, envIndex, rallyIndex)` 에서 시드 유도. **벡터 크기와 무관하다.**
- `proto/obs_spec.proto` — 관측 40차원의 단일 정의. 소비자는 Kotlin · Python · **(장래) JS**.
  정규화 상수가 숫자로 박혀 있어 다른 언어가 Kotlin 을 읽지 않고도 같은 관측을 만든다.

  플래그를 바꾸면 깨진다. 그것이 목적이다.
- 보상 항 5개가 이미 계산되어 `info` 로 나간다. **Phase 3 은 가중치만 올리면 된다.**

- `./scripts/bench-env.sh` — (a)(b)(c) 세 지점 측정.
- `deploy/compose/` — 엔진 서버 컨테이너 (UDS 볼륨 + TCP).

## 되짚을 만한 판단

- **결정론을 먼저 세우고 그 위에 의미론을 얹었다** (`plan.md` §1). Phase 1 과 달리 비교할
  정답이 없다. 관측이 맞는지는 증명할 수 없지만 어제의 관측과 오늘의 관측이 같은지는
  증명할 수 있다. 그래서 의미론이 자리 잡은 직후(P4) 에 해시를 박았다.
- **처리량 측정을 gRPC 보다 먼저 했다** (P5 → P6). 다 만든 뒤 "느리다" 를 마주하면 어디가
  느린지 알 수 없다. (a) 를 먼저 확정해 두니 (a)−(b)−(c) 의 뺄셈이 진단이 되었다.
- **`env` 가 gRPC 를 모르게 두고 빌드가 그것을 강제하게 했다** (`checkNoGrpc`).
  덕분에 서버 없이 (a) 를 잴 수 있고, 서버 결과가 in-process 와 바이트까지 같은지도 시험할 수 있다.
- **M2-g 를 셈이 아니라 불변식으로 풀었다** (`plan.md` §9). `core` 에 카운터를 넣는 대신
  `External` 슬롯은 `isComputer = false` 로 생성되므로 FSM 분기에 **들어갈 수가 없다.**
  더 싸고 더 확실하며 Phase 1 의 동치성을 건드리지 않는다.
- **bidi 스트리밍으로 가지 않았다.** unary 가 예산의 10.3% 만 쓴다. 예비안은 예비안으로 남았다.
  전환 여부를 짐작이 아니라 측정이 정했다.

## 작업 중 드러난 것 (문서를 수치에 맞춰 고친 것)

- **관측은 40차원이다.** `plan.md` §5.1 의 합계 41 은 산술 오류였다 (15+15+6+4).
  필드 목록이 실체이므로 구현을 40 으로 두고 유도 수치(관측 바이트, MLP 입력)를 고쳤다.
- **FSM vs FSM 800 게임의 랠리는 16,167 개다.** `PRD.md` §2.2 의 12,167 은 오타였다 —
  득점 합과 서브 전이 행렬 합이 모두 16,167 이다.
- **미러링은 오른쪽 슬롯에만 걸린다.** Track A 는 외부 슬롯이 왼쪽 하나뿐이라 미러링을 꺼도
  관측이 한 비트도 안 바뀐다. 골든의 `no-mirror` 케이스가 아무것도 시험하지 못하고 있었다.
- **서버는 단일 테넌트다.** 두 번째 `Configure` 가 첫 클라이언트의 구성을 조용히 갈아엎었다.
  세션 번호를 계약에 넣어 낡은 세션이 즉시 실패하게 했다.
- **macOS 에서는 TCP 루프백이 UDS 보다 빨랐다** (`plan.md` §7.3 의 전제와 반대).
  리눅스 epoll 에서는 뒤집힐 수 있다. 두 전송을 모두 지원하고 선택은 측정에 맡긴다.
