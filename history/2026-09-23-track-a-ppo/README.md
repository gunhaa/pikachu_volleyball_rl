# 2026-09-23 — track-a-ppo (ROADMAP Phase 3)

Phase 2 가 만든 gRPC 벡터 환경 위에 PPO 를 얹어, **랜덤 초기화에서 시작한 정책이
FSM(컴퓨터)을 이기게** 한 작업.

| 문서 | 답하는 질문 |
|---|---|
| [`PRD.md`](PRD.md) | 무엇을 만족해야 완료인가 |
| [`plan.md`](plan.md) | 어떻게 할 것인가 (판단과 근거) |
| [`tasks.md`](tasks.md) | 무엇부터 할 것인가 (P1~P7 체크리스트) |

이 작업의 본질은 "PPO 구현" 이 아니라 **무엇을 이겼다고 부를지 정하고 그것을 달성하는 것**
이었다. PPO 자체는 표준이고 위험하지 않다. 위험은 세 군데에 있었고 — 무엇을 재는가,
환경 규약을 조용히 틀리게 쓰는 것, 셰이핑이 목적을 갈아치우는 것 — 그래서 순서를
**"측정 → 평가 → 정확성 → 알고리즘 → 학습"** 으로 잡았다.

### 행동 분포 vs FSM (FR-11)

FSM 은 18개 중 **13개**만 쓴다 (Phase 2 측정): `(+1,0,0)` 48.2% · `(0,0,0)` 30.4% ·
`(−1,0,0)` 18.2% · 나머지 3.2%. 특히 `yDirection=+1`(아래)은 **powerHit 과 함께가 아니면
나오지 않는다** — y 축은 사실상 파워히트의 방향 지정용이다.

학습된 정책 (argmax, 진영별 60게임):

| 시드 | 왼쪽 | 오른쪽 | 합산 |
|---|---|---|---|
| 0 | 11/18 · x̄ **−0.411** · `(−1,0,0)`=.421 | 12/18 · x̄ −0.096 · `(0,0,0)`=.320 | 14/18 |
| 1 | 8/18 · x̄ **−0.559** · `(−1,0,0)`=.484 | 15/18 · x̄ +0.013 · `(+1,−1,0)`=.233 | 16/18 |
| 2 | 9/18 · x̄ **−0.173** · `(0,0,1)`=.252 | 13/18 · x̄ −0.026 · `(0,0,1)`=.292 | 14/18 |

세 가지가 보인다.

1. **정책은 FSM 이 쓰지 않는 조합을 쓴다.** `(−1,+1,0)` (아래 + powerHit 없음)이 시드 0 의
   왼쪽에서 17.2% 다. FSM 의 "y 는 파워히트 방향 지정용" 규칙 밖이다.
2. **진영별로 다른 정책을 낸다.** 왼쪽은 x 방향이 뚜렷이 음수 쪽(−0.17 ~ −0.56)이고
   행동 8~11개, 오른쪽은 거의 중립(−0.10 ~ +0.01)이고 12~15개다. 진영 플래그(FR-14)가
   실제로 쓰이고 있다는 직접 증거다.
3. **오른쪽이 더 다양한 행동을 쓴다.** PRD §2.4 가 잰 "오른쪽 진영이 20px 넓다"(196 vs 216)와
   일관된다 — 더 넓은 진영을 커버하려면 더 많은 수가 필요하다.

**샘플링 정책의 분포는 거의 균등하다** (엔트로피 2.78 / 균등 2.890, 18개 전부 사용).
엔트로피 보너스(0.02 → 0.002)가 확률을 평평하게 유지했는데도 argmax 는 완벽히 이긴다 —
**확률 분포는 평평한데 최빈 행동만 정확한** 정책이다.

### ⚠️ 이 승률을 순수한 실력 차로 읽으면 안 된다 (FR-11)

ROADMAP Phase 2 기록 4번: **FSM 은 에이전트보다 반 프레임 최신 정보를 본다.**
에이전트의 입력은 `runEngineForNextFrame` 호출 **전**에 정해지고, FSM 은 그 **안에서**
공이 이미 움직인 뒤에 결정한다 — 최대 20px 의 정보 우위다. 원작의 구조이므로 고치지 않는다.

즉 **Track A 의 100% 는 그 불리함을 안고 낸 결과**이고, 공정한 조건이었다면 격차는 더 컸다.
반대 방향의 착시는 없다 — 이 우위는 FSM 쪽에 있다.

- `evaluate.py` — 게임 단위 평가, 진영별·`combined`·`sideGap`, 미결 규칙, boldness 축.

  **스키마는 Phase 5 가 두 트랙을 겹쳐 그리는 전제**다.
- `track_a.py` — 러너. **알고리즘이 한 줄도 없다** — Track B 는 이 파일만 갈아 끼우면 된다.
- `scripts/train-track-a.sh` · `scripts/eval-policy.sh` — 학습·A/B·재개, 체크포인트 평가.
- `RandomBaselineTest.kt` · `BoldnessProbeTest.kt` — 기준선과 진단 행렬을 커밋된 테스트로.
- `EnvOptions.for_policy()` — 진영 플래그(41차원)와 절반 스왑을 **한 곳에서** 준다.

## 되짚을 만한 판단

- **평가기를 학습기보다 먼저 만들었다** (P3 → P6). RL 은 틀려도 돌아간다. 이 순서의 값은
  γ A/B 에서 정확히 치러졌다 — 세 런의 롤아웃 곡선은 구분이 안 되는데 평가는 .68 / .99 / .82
  로 갈렸다. 평가기가 없었다면 "차이가 없다" 고 결론 냈을 것이다.
- **롤아웃 테스트를 구현보다 먼저 썼다** (P4). 버려지는 스텝을 학습에 섞어도 **증상이 없다** —
  손실은 내려가고 보상 곡선은 올라간다. 증상 없는 버그는 나중에 "PPO 하이퍼파라미터가 나쁘다"
  로 오진되므로, 알고리즘을 얹기 전에 계약을 못 박았다.
- **예산을 하이퍼파라미터보다 먼저 쟀다** (P1). N·T·에폭·H 가 전부 예산의 함수인데 나중에
  재면 이미 고른 뒤다. 그리고 계획 단계의 추정("업데이트가 롤아웃보다 7~20배 비싸다")이
  **틀렸다는 것**을 그때 알았다 — 실측은 1.3~1.9배다.
- **MPS 를 쓰지 않았다.** P1 측정에서 업데이트가 2.1배 빨랐지만(종단 1.5배) 쓰지 않았다.
  이유는 속도가 아니라 재현성이다 — 목표를 이미 2배 넘긴 상태에서 M3-d 의 표면을 넓힐
  이유가 없다. 결과적으로 M3-d 는 13개 지표에서 불일치 0 이다.
- **프레임 스킵을 도입하지 않았다.** 결정 규칙("γ A/B 를 마치고도 정체하고 원인이 시간
  해상도로 특정될 때")을 미리 적어 뒀고, **규칙의 전제가 성립하지 않았다.**
  싸고 효과가 큰 손잡이였지만 근거가 없어서 넣지 않았다.
- **하이퍼파라미터를 하나도 조정하지 않았다.** `plan.md` §8.1 의 첫 설정이 목표를 넘겼다.
  H(128 → 256)도, 엔트로피 계수도, 에폭도 그대로다. **조정하지 않은 것도 기록이다.**

## 작업 중 드러난 것 (문서를 수치에 맞춰 고친 것)

1. **"boldness 커리큘럼 0 → 4" 가 성립하지 않는다** (ROADMAP 수정 대상이었다). b 를 0~4 로
   고정해도 무작위 정책의 랠리 승률이 .034 ~ .054 사이에서 단조성 없이 움직이고 게임 승은
   12개 조건 전부 0 이다. b 가 바꾸는 것은 난이도가 아니라 **랠리 길이**(2.4배)다.
   → 커리큘럼 축을 셰이핑으로 옮기고 boldness 는 진단 축으로만 썼다.
2. **⚠️ M3-h(truncation ≤ 2%)는 셰이핑 실패를 잡지 못한다.** `ball_touch` 를 6배로 키워
   승률이 .99 → .51 로 무너진 런에서도 `trunc = .0000` 이었다. 저글링 정책은 **랠리를
   안 끝낼 만큼 능숙해진 뒤에야** truncation 을 움직인다. 먼저 움직이는 것은 항별 기여
   비율이고(17% → 37%), 그것은 이미 `metrics.jsonl` 에 있다. `plan.md` §12 에 함정 13 으로 남겼다.
3. **⚠️ 미러링은 관측에만 걸리고 행동에는 걸리지 않는다.** 오른쪽 진영의 정책은
   "관측상 네트 방향" 과 "행동 `x=+1`" 이 반대인 상태로 학습한다. 진영 플래그 1비트가
   감당하는 것은 벽 비대칭(20px)만이 아니라 **행동 좌표계 반전까지**였다 —
   `plan.md` §4.5 는 이 사실을 몰랐고, 근거를 과소평가한 채로 옳은 결정을 했다.
4. **계획 단계의 비용 추정이 틀렸다** (`plan.md` §3.5). "업데이트가 롤아웃보다 7~20배 비싸다"
   → 실측 1.3~1.9배. 맞는 문장은 **"둘 다 목표를 넘겨서 어느 쪽도 건드릴 이유가 없다"** 였다.
5. **`torch.__version__` 은 `str` 이 아니다.** `TorchVersion` 객체이고 체크포인트에 그대로
   담으면 `weights_only=True` 로 읽히지 않는다 — **학습은 되는데 평가기가 그 체크포인트를
   못 읽는** 상태였다. "평가기가 읽을 수 있는가" 테스트가 잡았다.
6. **무한 랠리의 좌표가 바뀌었다.** `b=(0,4) seed=14` 는 커밋된 테스트의 시드 규약에서
   재현되지 않았고, 같은 현상을 내는 좌표는 `b=(0,1) seed=45` 다 (2,000,000 프레임까지
   끝나지 않는다). **현상과 결론은 그대로이고 예시만 교체됐다.**
