# PRD — track-a-ppo (ROADMAP Phase 3)

## 1. 개요

Phase 2 가 만든 gRPC 벡터 환경 위에 PPO 를 얹어, **랜덤 초기화에서 시작한 정책이 FSM(컴퓨터)을
이기게** 한다. 산출물은 `ppo.py` · `track_a.py` · 평가 스크립트이고, 완료 조건은
**양 진영 합산 게임 승률 ≥ 90% (학습 시드 3개 전부)** 다.

이 작업의 본질은 "PPO 구현" 이 아니라 **무엇을 이겼다고 부를지 정하고 그것을 달성하는 것**이다.
PPO 자체는 표준이고 위험하지 않다. 위험은 세 군데에 있다.

1. **무엇을 재는가** — 진영·게임 단위·시드 수를 정하지 않으면 승률이 실력이 아니라 진영을 잰다.
2. **환경 규약을 조용히 틀리게 쓰는 것** — next-step autoreset 의 버려지는 스텝을 학습에
   섞으면 손실 곡선은 멀쩡하게 내려가고 정책만 이상해진다.
3. **셰이핑이 목적을 갈아치우는 것** — 공 접촉에 값을 매기면 자기 진영에서 공을 저글링하는
   정책이 최적이 된다. 그 실패는 승률이 아니라 truncation 비율로 먼저 드러난다.

## 2. 배경

조사·측정으로 확인한 것만 적는다. 측정 절차와 원시 표는 `plan.md` §2 에 있다.

### 2.1 boldness 커리큘럼은 성립하지 않는다 — ROADMAP 수정 대상

ROADMAP 의 Phase 3 설명은 "boldness 커리큘럼 0 → 4" 다. 그 전제는 **틀렸다.**

`Player.computerBoldness` 를 0~4 로 고정하고 균등 무작위 정책을 100 게임씩 붙였다
(`plan.md` §2.1 의 전체 표):

| FSM boldness | 0 | 1 | 2 | 3 | 4 | 기본(무작위 추첨) |
|---|---|---|---|---|---|---|
| 무작위 정책의 랠리 승률 (왼쪽) | .0434 | .0341 | .0512 | .0518 | .0494 | .0446 |
| 〃 (오른쪽) | .0428 | .0415 | .0421 | .0434 | .0536 | .0482 |
| 게임 승 (200게임) | 0 | 0 | 0 | 0 | 0 | 0 |

랠리 ≈ 1,570개 기준 표준오차가 **±0.005** 다. 즉 위 숫자는 전부 잡음 안이고 **b 에 대한
단조성이 없다.** boldness 는 난이도 손잡이가 아니다.

> **P3 복원** — 이 표는 삭제된 임시 프로브의 것이고, `RandomBaselineTest.kt` 가 표본을 두 배로
> 늘려 커밋된 테스트로 다시 쟀다 (`plan.md` §2.1). **게임 승 0 과 "난이도 축이 아니다" 는 그대로**다.
> 다만 근거를 "잡음 안" 에서 **"폭이 작다"** 로 바꿨다 — b 가 움직이는 랠리 승률의 폭이
> 진영별로 .0130 / .0081 이다. 목표가 게임 승률 90% 인 축으로는 쓸 수 없다.

boldness 가 실제로 바꾸는 것은 **랠리 길이**다 (FSM vs FSM 평균 프레임):
`b=0 vs 0` 1,146 → `b=4 vs 4` 484. 2.4배다.

→ **커리큘럼의 축을 상대의 boldness 가 아니라 보상 셰이핑으로 옮긴다** (FR-6).
   boldness 는 학습 손잡이가 아니라 **진단 축**으로 쓴다 (FR-13).

### 2.2 boldness 를 고정하면 랠리가 끝나지 않을 수 있다

`FSM(b=0) vs FSM(b=4)`, seed 14 에서 **1,000,000 프레임을 넘겨도 랠리가 끝나지 않았다.**
기본 구성(라운드마다 재추첨)에서는 관측되지 않는다 — 두 FSM 의 boldness 가 매 랠리
갈리면서 균형이 깨지기 때문이다.

→ `maxRallyFrames` 는 편의 장치가 아니라 **필수 안전장치**다. 기본 3,000 을 유지한다.
   잘린 랠리 비율은 boldness 가 낮을수록 높다 (b=1 vs 0 에서 4.6%).

> **P3 정정** — 좌표가 바뀌었다. `b=(0,4) seed=14` 는 커밋된 테스트의 시드 규약에서 재현되지
> 않고, 같은 현상을 내는 좌표는 `b=(0,1) seed=45` (첫 서브 오른쪽) 다 — 2,000,000 프레임까지
> 끝나지 않는다 (`BoldnessProbeTest`). **현상과 결론은 그대로이고 예시만 교체됐다.**

### 2.3 Track A 의 출발 신호는 0 이 아니다

ROADMAP Phase 4 의 "랜덤 정책끼리는 공을 못 쳐 보상 신호가 없다" 는 **Track B 의 사실이고
Track A 에는 해당하지 않는다.** FSM 이 서브를 넣고 공을 되받아 주기 때문이다.

| | 왼쪽 | 오른쪽 |
|---|---|---|
| 랠리당 공 접촉 횟수 | 0.573 | 0.695 |
| 공을 한 번이라도 만진 랠리 | **36.5%** | **45.7%** |
| 랠리 승률 | 4.46% | 4.82% |
| 게임 승률 (100게임) | 0/100 | 0/100 |

→ 셰이핑은 **필수가 아니라 가속 장치**다. Track A 는 `rallyWin` 만으로도 기울기가 0 이
   아니다. 따라서 셰이핑은 작게 걸고 빨리 끄는 것이 기본값이고, 이것이 Track B(Phase 4)와
   정반대인 이유다.

### 2.4 진영 간 차이는 "벽 한 줄" 이고, 관측 2칸에 남는다

**대칭인 것** — 플레이어 시작 x (36 / 396), 가동 범위 (`[32,184]` / `[248,400]`),
서브 위치 (56 / 376), 네트 기둥 (216 ± 25). 전부 216 기준 정확히 대칭이다.

**비대칭인 것은 벽 반사 조건 한 줄뿐이다** (`PhysicsEngine.kt:424`):

```kotlin
if (futureBallX < BALL_RADIUS /* 20 */ || futureBallX > GROUND_WIDTH /* 432 */) { ... }
```

대칭이라면 오른쪽 조건은 `> 412` 여야 한다. 귀결은 **내 진영의 폭**이다 —
왼쪽 196px, 오른쪽 216px (**10.2% 차이**). FSM 끼리 왼쪽이 799/800 을 이기는 원인이 여기다.

미러링(`432 - x`) 후 관측에 남는 흔적:

```
네트       왼쪽 -0.049  │  오른쪽 -0.049   ← 같다
내 뒤쪽 벽  왼쪽 -1.000  │  오른쪽 -1.097   ← 20px = 0.097 차이
```

영향받는 필드는 40개 중 `ball.x` 와 `ball.expected_landing_point_x` **2개**다.
나머지 38개(내 몸·상대 몸·속도·상태·점수)는 대칭이다.

→ 두 가지를 정했다.

1. **양 진영에서 동시에 학습한다** (FR-3). 한쪽만 학습하면 M3-b 가 운에 걸린다.
2. **진영 플래그를 켠다** (FR-14, 관측 41차원). 미러링이 지운 1비트를 되살려, 정책이
   두 진영의 중간값으로 헤지하는 대신 진영별 위치 선정을 낼 수 있게 한다.

비대칭의 **가장 어려운 귀결은 이미 풀려 있다** — "벽에 맞고 어디 떨어지나" 는 엔진이 같은
비대칭 벽으로 앞서 시뮬레이션해 `expected_landing_point_x` 로 준다
(`PhysicsEngine.kt:501, 563`). 남는 것은 위치 선정 감각뿐이고, 그래서 1비트로 충분하다.
진영별로 정책을 둘 두는 안은 이 1비트를 사려고 **정책당 데이터를 절반**으로 줄이는 것이다
(`plan.md` §4.5 의 비교표).

### 2.5 처리량은 제약이 아니다 — 계산은 컴퓨트가 아니라 샘플 효율이 정한다

이 기계(Apple M2, 8코어, 16GB)에서 다시 잰 (c) 종단 처리량 (UDS, numpy MLP 40→256→256→18):

| N | env-step/s | 배치 | 정책 forward | 전송+서버 |
|---|---|---|---|---|
| 64 | 206,277 | 0.310 ms | 0.046 ms | 0.264 ms |
| 256 | 569,672 | 0.449 ms | 0.127 ms | 0.323 ms |
| **1024** | **896,352** | 1.142 ms | 0.450 ms | 0.692 ms |

전송 비용은 `0.235 ms + 0.446 µs × N` 로 맞는다 — **고정 지연이 지배한다**(Phase 2 의 결론과
같다). 따라서 N 은 클수록 좋다.

**P1 에서 torch 를 들이고 학습 한 반복 전체를 다시 쟀다** (`plan.md` §3 이 실측치로
교체됐다). N=512 · T=128 · H=128 · 진영 플래그 on 에서 **종단 ≈ 125,000 env-step/s** 이고,
그 안에서 롤아웃 40% · 그래디언트 업데이트 60% 다.

→ 계획 단계의 "업데이트가 롤아웃보다 7~20배 비싸다" 는 **틀렸다** — 실측은 1.3~1.9배다.
   맞는 문장은 **"둘 다 목표를 4배 넘겨서 어느 쪽도 건드릴 이유가 없다"** 이다.
   5천만 env-step 이 **7분**이다. **제약은 컴퓨트가 아니라 탐색과 샘플 효율**이고,
   GPU·분산은 오진이다. MPS 는 업데이트를 2.1배 빠르게 하지만(종단 1.5배) 쓰지 않는다 —
   목표를 이미 4배 넘긴 상태에서 재현성(M3-d)의 표면을 넓힐 이유가 없다 (NFR-5).

### 2.6 평가 비용은 정책이 세질수록 커진다

15점 게임 하나의 프레임 수: 무작위 정책 vs FSM **≈ 1,020**, FSM vs FSM **15,275**.
정책이 FSM 급이 되면 평가 한 번(양 진영 400게임씩)이 `800 × 15,275 ≈ 1,220만 env-step` 이다.
500k step/s 로 **약 25초** — 부담되지 않는다. 평가를 아낄 이유가 없다.

### 2.7 Phase 2 가 이미 해결해 둔 것

- **보상 가중치를 바꾸려고 서버를 다시 Configure 할 필요가 없다.** 서버는 `reward_terms` 로
  **항별 원시값**을 언제나 내보낸다. 가중치 적용과 어닐링은 전부 Python 쪽 산수다
  (`plan.md` §6). `Configure` 는 환경 상태를 버리므로 학습 중에 부를 수 없다 — 이 사실이
  아니었다면 어닐링이 불가능했다.
- 행동 공간 `Discrete(18)`, 관측 40차원, 레이아웃 해시 대조, 결정론(M2-d) 은 전부 서 있다.

## 3. 요구사항

### 3.1 기능 요구사항

| ID | 요구사항 |
|---|---|
| FR-1 | PPO (clipped surrogate, GAE(λ), 가치 손실, 엔트로피 보너스) 를 `ppo.py` 로 구현한다. 외부 RL 라이브러리에 의존하지 않는다 |
| FR-2 | 롤아웃 수집기가 **next-step autoreset 의 버려지는 스텝을 학습에서 제외**한다. 정책·가치·엔트로피 손실 전부에서 마스킹된다 |
| FR-3 | 학습은 **양 진영에서 동시에** 진행한다. 벡터의 절반은 왼쪽, 절반은 오른쪽 슬롯이다 |
| FR-4 | truncation 된 전이는 `V(s_final)` 로 부트스트랩하고, termination 은 하지 않는다 |
| FR-5 | 보상 가중치는 **클라이언트에서** `reward_terms` 에 적용한다. 학습 중 서버 재구성은 하지 않는다 |
| FR-6 | 셰이핑 가중치를 학습 진행도의 함수로 어닐링한다. 스케줄은 구성값이고 메트릭에 기록된다 |
| FR-7 | 게임 단위 평가기가 **양 진영 승률·합산·진영차(sideGap)** 를 낸다. `GameEvaluator` 와 같은 정의를 쓴다 |
| FR-8 | 체크포인트를 저장·복원한다. 평가는 체크포인트만으로 재현된다 |
| FR-9 | 메트릭을 run 단위 JSONL 로 남긴다. 최소 항목: 반복수, env-step, 정책/가치 손실, 엔트로피, KL, clipfrac, 설명분산, 랠리 승률, **항별 보상 기여 비율**, 랠리 길이, truncation 비율, 행동 분포 |
| FR-10 | 학습 시드를 인자로 받고, 같은 시드는 같은 결과를 낸다 |
| FR-11 | 최종 리포트에 **FSM 이 에이전트보다 반 프레임 최신 정보를 본다**는 사실(ROADMAP Phase 2 기록 4번)을 첨부한다 |
| FR-12 | 무작위 정책 기준선(§2.3) 을 Kotlin 테스트로 고정해 평가기의 자기 검증에 쓴다 |
| FR-13 | 평가기가 FSM 의 `computerBoldness` 를 고정할 수 있어야 한다. 커리큘럼용이 아니라 **진단용**이다 |
| FR-14 | 관측에 **진영 플래그를 포함한다** (`obs_include_side_flag = true`, 관측 41차원). Track B(Phase 4)도 같은 설정을 써야 Phase 5 의 동일 예산 비교가 성립한다 |

### 3.2 비기능 요구사항

| ID | 요구사항 |
|---|---|
| NFR-1 | 학습 종단 처리량 ≥ **60,000** env-step/s (N=512, M2, **그래디언트 업데이트 포함**). 롤아웃만의 수치가 아니다. P1 실측 125,000 의 절반이고, 남은 절반이 GAE·버퍼·메트릭·주기 평가의 몫이다 (`plan.md` §3.6) |
| NFR-2 | 5천만 env-step 학습이 벽시계 ≤ 60분. 한 시드 전체는 ≤ 6시간 |
| NFR-3 | Phase 1·2 의 골든(`./gradlew build`, `pytest`) 이 전부 초록으로 유지된다 |
| NFR-4 | FSM 을 부르는 Python 코드는 `track_a.py` 와 `evaluate.py` 에만 있다. `ppo.py` 는 상대가 누군지 모른다 (Phase 4 의 M4 불변식을 미리 지킨다) |
| NFR-5 | torch 는 CPU 를 기본으로 하고 스레드 수를 고정한다(4). MPS 는 P1 측정에서 업데이트 2.1배 이득이 **확인됐지만 쓰지 않는다** — 종단으로는 1.5배인데 목표를 이미 배로 넘겼고, 재현성(M3-d)의 표면만 넓어진다. 도입하려면 커널 결정론을 먼저 입증해야 한다 |
| NFR-6 | 체크포인트·메트릭·런 디렉터리는 커밋하지 않는다 |

## 4. 완료 조건 (Exit Criteria)

| ID | 지표 | 목표치 |
|---|---|---|
| **M3-a** | vs FSM **합산** 게임 승률 (양 진영 400게임씩) | **≥ 90%**, 학습 시드 3개 **전부** |
| **M3-b** | vs FSM **각 진영 단독** 게임 승률 | **≥ 80%** (합산 뒤에 한쪽의 실패를 숨기지 못하게) |
| M3-c | 평가 재현성 — 같은 체크포인트·시드로 두 번 평가 | 모든 집계 수치가 정확히 일치 |
| M3-d | 학습 재현성 — 같은 시드로 두 번 학습, 처음 20 반복 | 손실·KL 이 일치 |
| M3-e | 학습 종단 처리량 (N=512, 업데이트 포함) | ≥ **60,000** env-step/s, 측정치 기록 (P1 실측 ≈ 125,000) |
| M3-f | 롤아웃 정확성 — 버려지는 스텝이 손실에 0 기여 | 전용 테스트 통과 |
| M3-g | 평가기 자기 검증 — 무작위 정책 vs FSM | 게임 승 0/200, 랠리 승률 0.045 ± 0.010 (§2.3) |
| M3-h | 보상 해킹 감시 — 최종 정책의 랠리 truncation 비율 | ≤ 2% (넘으면 저글링 정책을 의심한다) |
| M3-i | Phase 1·2 회귀 | `./gradlew build` · `uv run pytest` 초록 |

**타협 불가**: M3-a 의 "양 진영" 과 "시드 3개". 한 진영만 재거나 시드 하나로 보고하는 것은
Phase 3 의 완료가 아니다. 진영은 교락변수이고(§2.4), 단일 시드의 RL 결과는 잡음이다.

**타협 가능**: M3-e 의 하한. 원래 30,000 은 `plan.md` §3 의 산수에서 유도한 값이었고
"±3배 틀릴 수 있다" 고 적혀 있었다. **P1 이 실측해 125,000 을 얻었고 하한을 60,000 으로
올렸다** (`plan.md` §3.6). 이후에도 이 문은 성능 경쟁이 아니라 **배선 사고 탐지기**다 —
P6 이 GAE·버퍼를 파이썬 루프로 짜면 여기서 걸린다.
**처리량은 이 Phase 의 목적이 아니다.** 진짜 제약은 컴퓨트가 아니라 샘플 효율이다.

## 6. 범위 밖 (Out of Scope)

| 하지 않는 것 | 어디로 | 단서 |
|---|---|---|
| 셀프플레이·상대 풀·리그 | Phase 4 | `ppo.py` 는 상대를 모르게 둔다. 그것이 Phase 4 가 재사용할 수 있는 조건이다 |
| Track A vs Track B 비교 | Phase 5 | 메트릭 JSONL 의 스키마는 두 트랙이 공유한다 |
| MySQL 적재 · 리플레이 뷰어 | Phase 6 | 평가기는 `(seed, 진영, 결과)` 를 남긴다. 입력 시퀀스 저장은 Phase 6 |
| ONNX export · k3s | Phase 7 | 평가는 gRPC 로 충분하다 (§2.6) |
| MLflow | Phase 5 | 지금은 JSONL. 런이 수십 개가 되는 시점이 도입 시점이다 |
| **프레임 스킵(action repeat)** | 조건부 | 학습이 정체하고 원인이 **시간 해상도**로 특정될 때만 도입한다. 도입하면 `env` 골든이 깨지는 것이 정상이고, 커밋 메시지에 이유를 적는다 (`plan.md` §9) |
| RNN·프레임 스택 | 조건부 | 관측이 마르코프에 가깝다(속도가 들어 있다). 성능이 모자란 이유가 부분관측으로 **측정되면** 그때 |
| 물리 엔진 수정 | 영구 | Phase 1 의 동치성이 전부의 근거다 |

## 7. 리스크

| 리스크 | 대응 |
|---|---|
| **셰이핑이 저글링 정책을 만든다** (자기 진영에서 공만 계속 침) | `ballTouch` 가중치를 `crossedNet` 보다 작게 잡고, truncation 비율을 매 반복 기록한다 (M3-h). 2% 를 넘으면 즉시 가중치를 내린다 |
| **오른쪽 진영이 80% 에 못 미친다** (§2.4) | 양 진영 동시 학습(FR-3)과 진영 플래그(FR-14)를 **처음부터** 켠다. 그래도 모자라면 진영별 2정책으로 간다 — 단 그 순간 정책당 데이터가 절반이 되고 Phase 4·5 의 동일 예산 비교 정의를 다시 써야 한다 (`plan.md` §4.5) |
| **Track B 가 진영 플래그를 빼먹어 Phase 5 비교가 무효가 된다** | 레이아웃 해시가 다르면 클라이언트가 붙는 즉시 실패한다 (Phase 2 의 `_verify_layout`). 그 위에, 러너들이 **공유하는 상수 하나**로 두어 애초에 갈라지지 않게 한다 |
| **긴 랠리에서 종단 보상이 사라진다** (γ=0.99 면 700프레임 뒤 0.0009) | γ 를 0.997 부터 시작하고 {0.99, 0.997, 0.999} 를 A/B 한다 (`plan.md` §5.2) |
| **버려지는 스텝을 학습에 섞는다** | 전용 테스트로 못 박는다 (M3-f). 구현보다 테스트를 먼저 쓴다 |
| **단일 시드의 우연을 결과로 보고한다** | 시드 3개를 완료 조건에 넣었다 (M3-a). 시드별 승률을 전부 보고한다 |
| **FSM 의 버릇에 과적합한다** | Track A 의 목표가 그것이므로 허용한다. 다만 boldness 별 승률(FR-13)을 보고해 과적합의 모양을 드러낸다 |
| **진영 분할 때문에 Phase 2 골든이 깨진다** | `swappedEnvs` 기본값 0 이면 기존 동작과 바이트 단위로 같다. 그것을 테스트로 고정한다 |
| **평가와 학습이 같은 서버를 쓰면 세션이 충돌한다** | 서버는 단일 테넌트다. 평가는 **별도 서버 프로세스**를 띄운다 (`plan.md` §7.3) |
