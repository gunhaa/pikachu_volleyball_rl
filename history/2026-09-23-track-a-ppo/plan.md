# plan — track-a-ppo (ROADMAP Phase 3)

`PRD.md` 의 요구사항을 **어떻게** 달성할지에 대한 기술 계획.

## 1. 접근 방식

**평가기를 학습기보다 먼저 만든다.**

RL 은 틀려도 돌아간다. 손실은 내려가고 보상 곡선은 올라가는데 정책은 엉뚱한 것을 배운
상태가 흔하다. 그래서 순서를 "알고리즘 → 실험 → 평가" 가 아니라 **"측정 → 평가 →
정확성 → 알고리즘 → 학습"** 으로 잡는다.

| 순서 | 무엇 | 왜 먼저인가 |
|---|---|---|
| 1 | 예산 측정 (torch 도입, 처리량·업데이트 비용) | 하이퍼파라미터가 예산의 함수다. 나중에 재면 이미 고른 뒤다 |
| 2 | 진영 분할 (env·proto·client) | 평가기와 학습기 **둘 다** 양 진영을 요구한다 (FR-3, FR-7) |
| 3 | 평가기 + 무작위 정책 기준선 | 학습 전에 "0%" 를 정확히 재 둔다. 이후 모든 숫자가 이 기준선과의 차이다 |
| 4 | 롤아웃 정확성 (autoreset 마스킹·GAE) | 여기가 틀리면 **조용히** 틀린다. 테스트를 구현보다 먼저 쓴다 |
| 5 | PPO 코어 | 위 넷이 서 있으면 표준 구현이고 위험이 없다 |
| 6 | 학습·튜닝 | 매 반복이 평가기로 즉시 채점되는 루프가 된다 |

Phase 1 이 "정답(JS)을 두고 차분" 했고 Phase 2 가 "정답이 없으니 결정론을 먼저" 했다면,
Phase 3 은 **"정답도 결정론도 없으니 기준선을 먼저"** 다.

## 2. 측정한 것

`engine-kotlin/env` 에 임시 프로브를 붙여 직접 쟀다 (측정 후 삭제, P3 에서 정식 테스트로

### 2.1 boldness 를 고정해도 FSM 의 강함은 변하지 않는다

`Player.initializeForNewRound()` 은 라운드마다 `computerBoldness = rand.next() % 5` 를
뽑는다 (`Physics.kt:191`). 이 값은 FSM 판단 5곳에 들어간다 (`PhysicsEngine.kt:279, 291,
300, 303, 313`) — 대기 전환 임계, 착지점 추적 데드존(`boldness + 8`), 점프 조건
(`ball.y < 10*boldness + 84`), 다이빙 조건(`boldness*5 + PLAYER_LENGTH`).

데드존이 커지면 위치 선정이 거칠어지고 점프는 많아지고 다이빙은 줄어든다. **어느 쪽이
센지는 코드만 보고는 알 수 없다.** 그래서 쟀다.

### 2.2 이 기계의 처리량 (재측정)

Apple M2 · 8코어 · 16GB. UDS, 더미 MLP(numpy, 40→256→256→18, 80,914 파라미터), 800 스텝.

| N | env-step/s | 배치 | 정책 forward | 전송+서버 |
|---|---|---|---|---|
| 64 | 206,277 | 0.310 ms | 0.046 ms | 0.264 ms |
| 256 | 569,672 | 0.449 ms | 0.127 ms | 0.323 ms |
| 1024 | 896,352 | 1.142 ms | 0.450 ms | 0.692 ms |

두 항을 N 에 대해 선형 적합하면

```
전송+서버 ≈ 0.235 ms + 0.446 µs × N      (고정 지연이 지배)
정책 forward ≈ 0.020 ms + 0.421 µs × N   (거의 순수 선형)
```

Phase 2 의 결론("비용의 정체는 데이터 양이 아니라 호출당 고정 지연")이 재확인됐다.
→ **N 은 크게 잡는다.** N=512 에서 전송 0.463 ms, numpy 정책 0.236 ms 로 예측된다.

### 3.2 (a) 정책 forward — 여기서도 고정 비용이 지배한다

`act()` = `log_softmax` + `multinomial` + `value`. 단독 측정, 200회 평균.

| H \ N | 256 | 512 | 1024 |
|---|---|---|---|
| 128 | 0.409 ms | 0.681 ms | 1.181 ms |
| 256 | 0.650 ms | 1.023 ms | 1.786 ms |

env 하나당 비용이 N 이 커질수록 **떨어진다** (H=128: 1.60 → 1.33 → 1.15 µs).
§2.2 의 gRPC 전송과 같은 모양이다 — 호출당 고정 비용이 지배한다. → **N 은 크게 잡는다.**

⚠️ 롤아웃 루프 **안에서는** 같은 forward 가 0.78~0.94 ms 다 (N=512, H=128).
단독 0.68 ms 와의 차이는 `from_numpy → act → .astype(uint8)` 왕복과 캐시다.
§8.2 의 uint8 함정은 실재하고, 크기는 롤아웃 비용의 약 1/4 이다.

### 3.3 (b) 스레드 수 — 4 가 최적이고 8 은 **더 느리다**

업데이트 한 반복(배치 65,536 · 에폭 4 · 미니배치 8, H=128):

| threads | 업데이트 | 샘플패스/s |
|---|---|---|
| 1 | 0.648 s | 404,802 |
| **4** | **0.312 s** | **839,555** |
| 8 | 0.322 s | 813,936 |

M2 는 성능 코어 4 + 효율 코어 4 다. 8 스레드는 **가장 느린 스레드가 배리어를 잡아**
4 스레드보다 느리다. "코어를 다 쓰면 빠르다" 는 작은 MLP 에서 성립하지 않는다.

→ `net.configure_torch(4)` 로 고정한다. 이 값은 성능이 아니라 **재현성**의 일부다
  (§11, M3-d) — 리덕션 순서가 스레드 수의 함수이기 때문이다. 체크포인트에 적는다.

### 3.4 (c)(d)(e) 한 반복의 벽시계

N=512, T=128 → 배치 65,536, 에폭 4, 미니배치 8, threads=4. (e) 는 실제 서버(UDS)로 잰
롤아웃 + 업데이트다.

| 구간 | H=128 | H=256 |
|---|---|---|
| 롤아웃 — 정책 | 0.100~0.120 s | 0.157 s |
| 롤아웃 — 전송·서버 | 0.064~0.117 s | 0.067 s |
| **업데이트 (CPU)** | **0.309~0.311 s** | **0.748 s** |
| 업데이트 (MPS, 참고) | 0.146 s | 0.301 s |
| **합계 (CPU)** | **0.47~0.55 s** | **0.97 s** |
| **종단 처리량** | **120,000~139,000 env-step/s** | **67,000** |

전송·서버의 폭은 **JVM JIT 워밍업**이다 — 같은 서버 프로세스에서 반복할수록
0.91 → 0.69 → 0.50 ms 로 내려간다. 정상 상태는 아래쪽이다.
(벤치를 매번 새 서버로 돌렸다면 이 값을 영영 못 봤을 것이다.)

### 3.5 계획 단계의 추정은 무엇이 틀렸나

| | 계획(원본 §3) | 실측 | |
|---|---|---|---|
| 업데이트 H=128 | 0.8 s | **0.31 s** | 2.6배 낙관 |
| 업데이트 H=256 | 2.6 s | **0.75 s** | 3.5배 낙관 |
| 롤아웃 | 0.12 s | **0.16~0.24 s** | 1.5~2배 비관 |
| **업데이트 / 롤아웃** | **7~20배** | **1.3~1.9배** (H=128) · 3.3배 (H=256) | **틀렸다** |
| 종단 처리량 | 69,000 | **~125,000** | 1.8배 |

두 방향으로 틀렸다. GFLOPS 가정(100 GFLOPS)은 작은 행렬에서 CPU 가 피크 근처에 간다고
본 것인데 실제로는 못 가고, 그 벌충을 넘어서게 **BLAS 가 잘했다**. 반대로 롤아웃 쪽은
torch 텐서 왕복 비용을 아예 빠뜨렸다.

**결론은 살아남았지만 근거가 바뀌었다.** "업데이트가 지배적이니 롤아웃을 건드릴 이유가
없다" 는 과장이었다. 맞는 문장은 **"둘 다 목표의 4배 위에 있으니 어느 쪽도 건드릴 이유가
없다"** 이다. 이 구분이 P4·P6 에서 중요하다 — 롤아웃이 전체의 40% 이므로,
GAE 나 버퍼 복사를 파이썬 루프로 짜면 종단 수치에 **바로** 드러난다.

### 3.6 귀결

- **종단 실측 ≈ 125,000 env-step/s** (H=128, N=512, 진영 플래그 on).
  → NFR-1 / M3-e 의 하한을 30,000 → **60,000** 으로 올린다. 실측의 절반이다.
    남은 절반은 P4·P6 이 얹을 것(GAE, 버퍼 복사, 메트릭, 주기 평가)의 몫이고,
    그것이 2배를 넘게 먹으면 배선이 잘못된 것이므로 빨간불이 맞다.
    (하한을 실측치 그대로 두지 않는 이유: 그러면 기계 상태를 재는 깨지기 쉬운 문이 된다.)
- 5천만 env-step ≈ **7분**. 5억 ≈ 70분. NFR-2(한 시드 ≤ 60분)는 8배 여유다.
- **H=256 도 예산 안이다** (67,000 = 목표의 2.2배). 그러므로 H=128 로 시작하는 이유는
  이제 예산이 아니라 **샘플 효율**이다 — 작은 망이 적은 데이터로 더 빨리 움직인다.
  올릴 근거는 "느려서" 가 아니라 "정체의 원인이 표현력으로 특정될 때" 다.
- **MPS 는 업데이트를 2.1배 빠르게 한다** — §12 의 함정 11 이 이 구간에서는 **틀렸다.**
  그런데도 CPU 로 간다 (NFR-5). 종단으로는 0.52 → 0.35 s (1.5배)이고, 목표를 이미 4배
  넘긴 상태에서 1.5배를 사려고 **재현성(M3-d)의 표면**을 넓힐 이유가 없다.
  MPS 의 커널 결정론과 리덕션 순서는 CPU 만큼 보장되지 않는다.
  이득이 필요해지는 시점(예: Phase 4 의 셀프플레이가 훨씬 큰 예산을 요구할 때)에
  다시 꺼내 쓸 수 있도록 측정만 남긴다.
- 에폭 4 · 미니배치 8 을 줄일 이유가 **없다.** 계획의 "예산 미달 시 에폭부터 줄인다" 는
  발동 조건이 오지 않았다.

## 4. 양 진영을 동시에 학습한다

### 4.1 진영 간 차이의 정확한 크기

`PRD.md` §2.4 — 비대칭은 **벽 반사 조건 한 줄**(`PhysicsEngine.kt:424`)이고, 귀결은
**내 진영의 폭이 왼쪽 196px · 오른쪽 216px (10.2% 차이)** 라는 것이다. 플레이어 시작
위치·가동 범위·서브 위치·네트는 전부 216 기준 정확히 대칭이다.

미러링 후 관측에 남는 흔적을 숫자로:

| | 왼쪽 슬롯 | 오른쪽 슬롯 |
|---|---|---|
| 네트가 보이는 좌표 | −0.049 | −0.049 |
| 내 뒤쪽 벽 | −1.000 | **−1.097** |
| 상대 뒤쪽 벽 | +1.000 | **+0.903** |

즉 **네트는 같은 자리에 보이고 뒷벽만 20px 움직인다.** 영향받는 필드는 40개 중
`ball.x` 와 `ball.expected_landing_point_x` 두 개다.

같은 상대 기하(내 벽에서 거리 d)를 두 진영이 볼 때의 관측 차이는 상수 −0.097 이다:

```
왼쪽   f(20 + d) = 2d/412 − 1
오른쪽 f(432 − d) 미러 후 = 2d/412 − 1 − 40/412 = (2d/412 − 1) − 0.097
```

한쪽에서만 학습하면 다른 쪽에서 이 상수만큼 분포 밖을 본다. 그래서 **양 진영에서 동시에**
학습한다. 완료 조건도 진영별로 걸려 있다 (M3-b, 각 진영 ≥ 80%).

### 4.2 선택지

| 안 | 방법 | 비용 | 판정 |
|---|---|---|---|
| A | 왼쪽만 학습하고 오른쪽은 전이에 맡긴다 | 0 | ✗ M3-b 가 운에 걸린다 |
| B | 반복마다 `Configure` 로 진영을 바꾼다 | 0 | ✗ `Configure` 는 환경 상태를 버린다. 매번 0:0 에서 다시 시작하는 분포가 된다 |
| C | 서버 프로세스 2개(진영당 1개) + Python 병합 | JVM 2개, 배치당 RPC 2회 | △ proto 무변경이지만 고정 지연(0.235 ms)을 두 번 낸다 |
| **D** | **한 서버 안에서 env 를 진영별로 나눈다** | proto 1필드 + Kotlin ~20줄 | **✓ 채택** |

D 가 성립하는 이유: **진영을 바꿔도 외부 슬롯 수가 변하지 않는다.**
`(External, Fsm)` 도 `(Fsm, External)` 도 `slotCount == 1` 이므로 packed 바이트 레이아웃이
균일하게 유지된다. 이것이 아니었다면 D 는 불가능했다.

### 4.3 실행 구조

```kotlin
// VectorEnv.kt — 뒤쪽 swappedEnvs 개의 환경만 진영을 뒤집는다.
class VectorEnv(config: EnvConfig, val numEnvs: Int, val swappedEnvs: Int = 0) {

    private fun configFor(i: Int): EnvConfig =
        if (i >= numEnvs - swappedEnvs) config.copy(slots = Slots(config.slots.p2, config.slots.p1))
        else config

    init {
        require(swappedEnvs in 0..numEnvs)
        // 스왑이 슬롯 수를 보존한다는 것이 packed 레이아웃의 전제다. 구조로 못 박는다.
        check(configFor(0).slotCount == configFor(numEnvs - 1).slotCount)
    }

    private var envs = Array(numEnvs) { PikaEnv(configFor(it), it) }
}
```

```proto
// env.proto
message ConfigureRequest {
  // ...
  // 뒤쪽 이만큼의 환경은 p1/p2 를 뒤바꿔 쓴다. 기본 0 = 전부 (p1, p2).
  // 슬롯 수가 보존되므로 바이트 레이아웃은 균일하다.
  optional int32 swapped_envs = 12;
}
```

```python
# env_client.py — 점수 해석이 env 마다 달라진다.
def _sides(p1: str, p2: str) -> list[int]:
    return [side for side, kind in enumerate((p1, p2)) if kind == "external"]

normal, swapped = _sides(o.p1, o.p2), _sides(o.p2, o.p1)
self._slot_side = np.array(
    [normal] * (n - o.swapped_envs) + [swapped] * o.swapped_envs, dtype=np.intp,
)  # shape (server_num_envs, slot_count)
```

**기본값 0 이면 기존 동작과 바이트 단위로 같다.** P2 의 확인 항목이 그것이다.

### 4.4 함정

- ⚠️ `swapped_envs` 를 **앞쪽**이 아니라 뒤쪽에 두는 이유: `deriveSeed(baseSeed, envIndex, k)`
  가 envIndex 를 쓰므로, 앞쪽을 바꾸면 기존 시드 배치가 통째로 이동해 Phase 2 의 결정론
  골든(M2-d)과 비교가 불가능해진다.
- ⚠️ `EnvConfig.copy(slots = ...)` 로 만든 구성은 `layoutHash` 가 같다 — 관측 레이아웃은
  슬롯 구성과 무관하기 때문이다. 해시 대조(`_verify_layout`)는 그대로 유효하다.
- ⚠️ 학습 배치 안에서 **앞 절반과 뒤 절반의 분포가 다르다.** 진영별 메트릭을 따로 찍지
  않으면 한쪽의 실패가 평균에 묻힌다 (FR-9).

### 4.5 진영 플래그를 켠다 — 미러링이 지운 1비트를 되살린다

양 진영에서 학습해도 **정책은 자기가 어느 진영인지 모른다.** 미러링이 그 정보를 지우기
때문이다. 그러면 §4.1 의 20px 차이에 대해 정책은 두 진영의 **중간값으로 헤지**하게 된다.

| 안 | 정책이 받는 데이터 | 비대칭 대응 | 비용 |
|---|---|---|---|
| A. 미러링만 | 전량 | ✗ 헤지 | 0 |
| **B. 미러링 + 진영 플래그** | 전량 | ✓ 1비트로 진영별 행동 | **0 — 이미 구현되어 있다** |
| C. 진영별 2정책 | **절반씩** | ✓ | 파라미터 2배, Phase 4 의 상대 풀과 Phase 5 의 동일 예산 비교 정의를 다시 써야 한다 |

**B 를 채택한다.** 두 진영이 공유하는 것(타격 타이밍·점프·파워히트·상대 읽기 — 관측 38/40)을
C 는 각자 독립으로 다시 배운다. 차이가 2개 필드의 상수 오프셋이라면 그 대가를 치를 이유가 없다.

비용이 0 인 이유:

- 플래그는 이미 `Configure` 필드다 (`obs_include_side_flag`). proto·Kotlin 변경이 없다.
- `ObsEncoder` 가 이미 **플래그만은 미러링하지 않는다** — 주석이 그 의도를 적어 두었다.
- **Phase 2 의 골든 11 케이스에 `includeSideFlag = true` 가 이미 들어 있다**
  (`EnvGolden.kt:95`). `EnvGoldenRegressionTest.kt:61` 이 그 케이스의 존재를 단언한다.
  → **골든이 깨지지 않는다.** 러너가 `True` 를 넘기면 끝이다.

⚠️ **Track B(Phase 4)도 반드시 같은 설정을 써야 한다.** 관측 공간이 다르면 두 트랙은 다른
문제를 푼 것이고 Phase 5 의 동일 예산 비교가 무효가 된다. 어긋나면 레이아웃 해시 대조가
붙는 즉시 실패시키므로(`_verify_layout`) 조용히 틀릴 수는 없지만, **러너들이 공유하는 상수
하나**로 두어 애초에 갈라지지 않게 한다.

⚠️ 관측 차원이 **40 → 41** 이 된다. §8.1 의 망 입력 차원과 §3 의 예산 산수가 이 값을 쓴다.

**P2 의 구현 (2026-09-23)**: 상수 하나로는 모자랐다. 상수는 **참조를 잊을 수 있고**,
잊었다는 사실은 승률이 이상해지기 전까지 드러나지 않는다. 그래서 구성 **생성**을 한 곳으로
묶었다 — `EnvOptions.for_policy()` 가 `OBS_INCLUDE_SIDE_FLAG` 와 `swapped_envs = num_envs // 2`
를 함께 준다. 러너는 이 하나만 부른다. `EnvOptions` 자체의 기본값은 **서버 기본값 그대로**
두었다 (그 동치는 `test_layout_hash_matches_server` 가 지키는 별개의 계약이다).

## 5. 시간 구조 — γ 와 T

### 5.1 랠리 길이는 학습 중에 10배 늘어난다

| 상대 구성 | 평균 랠리 프레임 |
|---|---|
| 무작위 정책 vs FSM | **65** (§2.1) |
| FSM vs FSM | **759** (Phase 2 측정) |

정책이 세질수록 랠리가 길어진다. 즉 **에피소드 길이가 학습의 함수**다. 이것이 두 가지를 정한다.

### 5.2 γ 를 0.997 로 잡는다

종단 보상 ±1 이 랠리 시작까지 얼마나 살아남는가:

| γ | 65 프레임 | 300 | 700 | 3,000 (상한) |
|---|---|---|---|---|
| 0.99 | 0.52 | 0.049 | **0.0009** | ~0 |
| **0.997** | 0.82 | 0.41 | **0.12** | 0.0001 |
| 0.999 | 0.94 | 0.74 | 0.50 | 0.05 |

γ=0.99 는 학습 초반(65프레임)에는 충분하지만 **후반(700프레임)에 신호가 사라진다.**
γ=0.999 는 신호를 보존하는 대신 가치 추정 분산이 커진다. **0.997(유효 지평 333프레임 ≈ 13초)
로 시작하고 {0.99, 0.997, 0.999} 를 A/B 한다** (P6).

25 FPS 라는 사실이 여기서만 쓰인다 — 333 프레임은 사람이 "한 랠리의 한 국면" 으로 느끼는 길이다.

> **P6 측정 — 예측이 맞았다.** 1000만 step · 시드 0 · 최종 평가 진영별 100게임:
>
> | γ | 합산 게임승 | 왼쪽 | 오른쪽 | 진영차 | argmax 랠리승률 | 롤아웃 랠리승률(10M) |
> |---|---|---|---|---|---|---|
> | 0.99 | .8200 | .6700 | .9700 | −.3000 | .5240 | .564 |
> | **0.997** | **.9900** | **1.0000** | **.9800** | **+.0200** | **.6870** | .604 |
> | 0.999 | .6800 | .3600 | 1.0000 | −.6400 | .5342 | .567 |
>
> ⚠️ **롤아웃 지표로는 셋을 구분할 수 없다.** 샘플링 정책의 랠리 승률은 .564 / .604 / .567
> 로 거의 같은데 argmax 평가는 .68 ~ .99 로 갈린다. 차이는 **결정론 정책에서만** 나타난다 —
> argmax 는 거의 결정론적인 FSM 을 상대로 특정 국면에 반복해서 갇힐 수 있고, 갇히는 자리가
> 진영마다 다르다 (γ=0.999 의 왼쪽 .36 / 오른쪽 1.00 이 그 모습이다).
>
> → 이것이 **P3 을 P6 보다 먼저 한 이유의 값**이다. 평가기가 없었다면 세 런의 학습 곡선을
>   겹쳐 놓고 "차이가 없다" 고 결론 냈을 것이다.

### 5.3 T = 128

- 학습 초반: 세그먼트당 랠리 종료가 ~2회 → 종단 보상이 배치 안에 충분히 들어온다.
- 학습 후반: 랠리가 T 보다 길어 세그먼트에 종료가 없는 env 가 생긴다. 정상이다 —
  그때는 GAE 가 부트스트랩으로 잇는다. 그래서 **truncation 부트스트랩이 맞아야 한다** (§6.3).

## 6. 보상 — 가중치는 서버가 아니라 클라이언트에 있다

### 6.1 왜 클라이언트인가

셰이핑 어닐링은 가중치를 **반복마다** 바꾸는 일이다. 서버의 `RewardWeights` 를 바꾸려면
`Configure` 를 다시 불러야 하는데 그것은 **환경 상태를 전부 버린다** (`EnvService` 가
`VectorEnv` 를 새로 만든다). 매 반복 리셋하면 정책은 랠리 초반만 보게 된다.

그런데 서버는 `reward_terms` 로 **항별 원시값을 언제나** 내보낸다 (Phase 2 의 FR-6).
가중 합계는 Python 에서 하면 된다.

```python
# 서버의 reward 필드는 학습에 쓰지 않는다. 항별 값에 현재 가중치를 곱한다.
terms = env.reward_terms          # (num_envs, 5) — rally_win, ball_touch, crossed_net,
                                  #                 opponent_miss, time_penalty
reward = terms @ w_now            # w_now 는 이 반복의 스케줄 값
```

→ **서버 구성은 학습 내내 한 번도 바뀌지 않는다.** `rally_win=1` 기본값 그대로 두고 무시한다.

⚠️ `info[name]` 은 클라이언트가 **재사용하는 버퍼의 뷰**다 (`env_client.py:281`).
버퍼에 그대로 담으면 다음 스텝에 덮어쓰인다. `PikaVectorEnv` 에 `(N, 5)` 배열을 돌려주는
`reward_terms` 프로퍼티를 추가하고, 롤아웃 버퍼에는 **복사해서** 담는다.

### 6.2 스케줄

`PRD.md` §2.3 이 말한 대로 Track A 의 출발 신호는 0 이 아니다(랠리 승률 4.5%, 접촉 37%).
따라서 셰이핑은 **작게 걸고 빨리 끈다**.

| 항 | 가중치 | 역할 | 어닐링 |
|---|---|---|---|
| `rally_win` | 1.0 | 진짜 목적 | 고정 |
| `crossed_net` | 0.10 | 공을 **넘기는** 것에 값을 매긴다 | 0~20% 구간 유지 → 50% 에서 0 |
| `ball_touch` | 0.05 | 공에 닿는 것 | 〃 |
| `opponent_miss` | 0 | `rally_win` 과 중복이다 | — |
| `time_penalty` | 0 | 랠리를 짧게 만드는 힘이 이미 있다 | — |

**`crossed_net` 이 `ball_touch` 보다 큰 것이 핵심이다.** 반대로 두면 자기 진영에서 공을
계속 치는 것이 최적 전략이 된다 — 그 정책은 랠리를 끝내지 않으므로 **truncation 비율로
먼저 드러난다** (M3-h, 임계 2%).

크기 감각: 65프레임 랠리에서 셰이핑 기댓값은 `0.573 × 0.05 + (넘긴 횟수) × 0.10` ≈ 0.05~0.1
이고 `rally_win` 은 ±1 이다. **셰이핑은 순위를 바꾸지 않고 기울기만 촘촘하게 한다.**
이것이 의도한 비율이다.

> **P6 측정 — 방향은 맞았고, 감시 지표는 틀렸다.** γ=0.997 · 1000만 step · 시드 0:
>
> | 셰이핑 (`crossed_net` / `ball_touch`) | 합산 | 왼쪽 | 오른쪽 | 랠리승률 | **trunc** | 셰이핑 최대 기여 |
> |---|---|---|---|---|---|---|
> | 없음 (0 / 0) | .9500 | 1.0000 | .9000 | .6497 | .0000 | 0% |
> | **기본 (0.10 / 0.05)** | **.9900** | **1.0000** | **.9800** | **.6870** | **.0000** | **17%** |
> | 뒤집기 (0.05 / 0.30) | .5100 | .3600 | .6600 | .5003 | .0000 | **37%** |
>
> 1. **기본값이 최선이다.** 셰이핑을 끄면 −.04, 뒤집으면 −.48 이다. "가속 장치" 라는
>    성격도 확인됐다 — 없어도 .95 는 나온다 (PRD §2.3 이 말한 대로 출발 신호가 0 이 아니다).
> 2. ⚠️ **M3-h 는 뒤집힌 런을 잡지 못했다.** 저글링 정책을 예상하고 truncation 비율을
>    감시 지표로 걸었는데, 세 런 모두 `trunc = .0000` 이다. 실패는 랠리 승률이 **정확히
>    .5003 에 정체**하는 모습으로 나타났다 — 공을 만지는 것에 최적화되면서 이기는 법을
>    덜 배웠고, **랠리를 안 끝낼 만큼 능숙해지지도 못했다.**
>
> → **감시 지표를 하나 더 둔다**: 항별 기여 비율(`term_share`). 셰이핑이 보상의 30% 를
>   넘으면 그 시점에 이미 목적이 갈아치워지고 있다. truncation 은 그보다 **한참 뒤에**,
>   정책이 저글링을 실제로 해낼 만큼 능숙해져야 움직인다. `metrics.jsonl` 에 매 반복
>   기록되므로 추가 계측은 필요 없다 (FR-9).

### 6.3 truncation 부트스트랩

| 플래그 | 목표값 | 이유 |
|---|---|---|
| `terminated` | `r_t` | 에피소드가 정말 끝났다. 이후 가치는 0 |
| `truncated` | `r_t + γ·V(s_final)` | 랠리는 계속될 수 있었다. 자르는 것은 우리 사정이다 |

**next-step autoreset 덕분에 `s_final` 이 그냥 손에 들어온다.** `step()` 이 돌려준 관측이
곧 `s_final` 이기 때문이다. 구 API(same-step autoreset)였다면 그 자리에 새 에피소드의 첫
관측이 들어와서 `info["final_observation"]` 을 뒤져야 했다.

## 7. 롤아웃 — 버려지는 스텝을 학습에서 지운다

### 7.1 타임라인

| 스텝 | 우리가 넣은 obs | 서버가 하는 일 | 돌려주는 obs | reward | term/trunc |
|---|---|---|---|---|---|
| t−1 | `s_{T-1}` | 물리 한 프레임 | `s_T` (랠리 마지막) | 종단 보상 | **1** |
| **t** | `s_T` | **리셋**. 행동을 버린다 | `s'_0` (새 랠리 첫 관측) | **0** | 0 |
| t+1 | `s'_0` | 물리 한 프레임 | `s'_1` | … | 0 |

스텝 t 의 전이 `(s_T, a_t, 0, s'_0)` 는 **에피소드를 가로지르는 가짜 전이**다.
학습에 섞으면 "랠리가 끝난 상태에서 아무 행동이나 하면 보상 0 이고 다음은 초기 상태"
라는 것을 배우고, 가치 함수는 종단 상태의 값을 초기 상태 쪽으로 끌어당긴다.

**손실 곡선은 멀쩡하다.** 그래서 테스트로 못 박는다 (M3-f).

### 7.2 실행 구조

```python
# rollout.py — 핵심만
pending = self.pending          # 직전 스텝의 (terminated | truncated), 롤아웃 사이에 유지된다
for t in range(T):
    valid[t] = ~pending         # 이 전이를 학습에 쓰는가
    with torch.no_grad():
        action, logp, value = net.act(obs)
    obs_next, _, term, trunc, _ = env.step(action.numpy().astype(np.uint8))

    obs_b[t], act_b[t], logp_b[t], val_b[t] = obs, action, logp, value
    rew_b[t] = env.reward_terms @ w_now          # §6.1 — 복사본이다
    term_b[t], trunc_b[t] = term, trunc

    pending = term | trunc
    obs = obs_next
self.pending = pending
```

```python
# GAE — cut 은 "에피소드가 여기서 끝났다", valid 는 "이 전이를 배우는가"
last_gae = 0
for t in reversed(range(T)):
    next_value = val_b[t + 1] if t + 1 < T else bootstrap_value   # = V(돌려받은 obs)
    cut = term_b[t] | trunc_b[t]
    delta = rew_b[t] + gamma * next_value * (1 - term_b[t]) - val_b[t]
    last_gae = delta + gamma * lam * (1 - cut) * last_gae
    adv[t] = last_gae
returns = adv + val_b
# 손실은 valid 로 마스킹한다 (정책·가치·엔트로피 전부).
```

읽을 것:

- `next_value` 에 곱하는 것은 `(1 - terminated)` 이지 `(1 - cut)` 이 아니다.
  truncated 는 부트스트랩해야 한다 (§6.3).
- `last_gae` 를 끊는 것은 `(1 - cut)` 이다. 버려지는 스텝 t+1 로 재귀가 새지 않는다.
- 버려지는 스텝 자신의 `adv` 는 쓰레기지만 `valid=False` 라 손실에 들어가지 않고,
  `cut[t]=1` 이라 앞으로도 전파되지 않는다.

### 7.3 비용

버려지는 스텝의 비율은 `1 / (평균 랠리 길이 + 1)` 이다.
학습 초반(65프레임) **1.5%**, 후반(700프레임) **0.14%**. 무시할 수 있다.

### 7.4 P4 가 실제로 만든 것

| 파일 | 역할 |
|---|---|
| `rollout.py` | `compute_gae` · 마스킹 도우미 · `RolloutBatch` · `RolloutCollector` · 진영별 메트릭 |
| `schedules.py` | `Piecewise`/`Linear`/`Constant` 와 `RewardWeighting` (항별 스케줄 → 가중치 벡터) |
| `test_rollout.py` | 32개. 31개는 서버 없이 돌고, 마지막 하나만 실제 서버에 붙는다 |

계획에 없었고 만들면서 정한 것 다섯:

**1. `cut` 이 끊는 방향을 테스트가 정정했다.** `cut[t]=1` 은 "t 가 t+1 의 advantage 를
흡수하지 않는다" 이지 "t−1 이 t 를 흡수하지 않는다" 가 아니다. 종료 스텝의 advantage 는
유효한 학습 신호이고 그 **앞** 스텝은 그것을 정상적으로 받는다. 귀결: truncation
부트스트랩의 이득은 종료 스텝에만 머무르지 않고 `γλ` 로 앞으로 번진다 (손계산 예제에서
`+1.0` 다음 칸이 `+0.25`). 처음 쓴 기대값은 이 방향을 한 칸 밀어 써서 붉었다.

**2. `masked_mean` 은 마스크가 비면 0 을 낸다.** `x[mask].mean()` 은 그 경우 NaN 이고,
NaN 한 번이면 역전파가 망 전체를 죽인다. 미니배치가 통째로 버려지는 스텝일 확률은 낮지만
0 이 아니고, 그 사고는 학습 몇 시간 뒤에 일어난다.

**3. advantage 정규화는 모분산을 쓴다.** 마스크 안에서 ddof 를 다시 세는 복잡함을 살
이유가 없다 — 미니배치 8,192 에서 표본분산과의 차이는 1e-4 다.

**4. 가중치 벡터는 서버가 선언한 항 순서로 만든다** (`RewardWeighting`). `[1.0, 0, 0.1, 0, 0]`
처럼 배열을 직접 쓰면 서버가 항을 하나 추가하는 날 가중치가 통째로 밀리고, 모르는 항 이름은
"가중치 0" 으로 조용히 흡수된다. 둘 다 승률이 이상해지기 전까지 드러나지 않는다.

**5. 진영 행 인덱스를 `slot_sides` 에서 읽는다** — "앞 절반이 왼쪽" 을 가정하지 않는다.
그 배치는 `swapped_envs` 의 구현 세부이고 (plan.md §4.4 는 뒤쪽을 스왑한다), 수집기가
그것을 다시 가정하면 규약이 두 곳에 생긴다.

그리고 **서버를 띄우는 테스트는 하나뿐이다.** 나머지는 `ScriptedEnv` 로 `PikaEnv` 의
오토리셋 상태기계만 흉내낸다 — 실제 서버로는 "랠리가 정확히 여기서 끝나는" 상황을 만들 수
없기 때문이다. 대신 그 하나가 계약의 접합(관측 41차원, `reward_terms` 모양, `slot_sides`
길이, uint8 행동, 경계를 넘는 `pending`)을 지킨다. 통계는 보지 않는다.

- ⚠️ **advantage 정규화를 마스크 밖까지 포함해 계산하면** 버려지는 스텝의 쓰레기

- ⚠️ 행동은 서버에 **uint8** 로 간다. torch 의 `int64` 샘플을 그대로 넘기면
  `env_client.py` 가 범위 검사 후 변환하지만, 변환 비용이 핫 패스에 얹힌다.
- ⚠️ `torch.set_num_threads()` 를 명시한다. 기본값(코어 수)이 작은 MLP 에서 오히려 느릴 수
  있고, 스레드 수가 곧 **재현성**을 좌우한다 (M3-d). P1 에서 1·4·8 을 잰다.

### 8.3 P5 가 실제로 만든 것

| 파일 | 역할 |
|---|---|
| `ppo.py` | `PPOConfig` · `compute_losses` · `approx_kl` · `explained_variance` · `PPOUpdater` |
| `test_ppo.py` | 19개. 서버도 환경도 띄우지 않는다 |

계획에 없었고 만들면서 정한 것 넷:

**1. 가치 손실은 순수 MSE 다.** 흔한 구현은 `0.5 × MSE` 를 만든 뒤 다시 `value_coef = 0.5`
를 곱한다. 그러면 표(§8.1)의 0.5 가 실제로는 0.25 를 뜻하게 되고, P6 이 이 계수를 A/B 할 때
무엇을 재는지 알 수 없어진다. **가치 손실 클리핑도 넣지 않았다** — §8.1 의 표에 없고,
효과가 논쟁적인 손잡이를 근거 없이 늘리면 설명해야 할 축만 는다.

**2. 근사 KL 은 `(r − 1) − log r` 이다** (Schulman 의 k3). `−mean(log r)` 은 불편추정이지만
**음수가 될 수 있고 분산이 크다.** 조기 종료 문턱(0.02)이 그 잡음 위에 서면 어떤 반복은
4에폭을, 어떤 반복은 1에폭을 돌고, 그 차이는 하이퍼파라미터가 아니라 운이다.

**3. 조기 종료는 에폭 경계에서 판정한다.** 미니배치마다 끊으면 그 반복이 실제로 본 데이터가
**셔플 순서의 함수**가 된다 — 같은 시드에서만 재현되는 결과가 되고, M3-d 는 통과하면서
결과의 의미는 흐려진다.

**4. NFR-4 는 AST 로 검사한다.** 원문 문자열 검색으로 "side" 를 금지하면 `consider` 에
걸린다. 그리고 모듈 docstring 은 "FSM 을 모른다" 고 **말해야** 한다. 그래서 (1) 프로세스를
띄워 `grpc` · `gymnasium` · `env_client` · `evaluate` 가 `sys.modules` 에 없음을 보고
(2) AST 에서 식별자만 걷어 금지어를 찾는다.

그리고 **부호 배선을 종단으로 한 번 확인한다**: 한 행동에만 `A > 0` 을 주고 20번 업데이트하면
그 행동의 확률이 오른다. 정책 손실 부호·엔트로피 부호·옵티마이저 방향 중 **어느 하나가
뒤집혀도 손실은 내려가므로**, 손실이 아니라 확률을 직접 본다.

## 9. 평가

### 9.1 게임 경계를 어떻게 아는가

`PikaEnv` 는 게임이 끝나면 **스스로 다음 게임을 시작한다** (`startGame()`).
Python 쪽은 `info` 의 점수로 경계를 읽는다.

```python
# 랠리가 끝난 스텝에서만 점수가 오른다.
finished = terminated & ((score_me >= winning_score) | (score_opp >= winning_score))
wins += (finished & (score_me >= winning_score)).sum()
```

`GameEvaluator` 와 같은 정의다 — 15점 선취, 진영별 집계, `combined = (asLeft + asRight)/2`,
`sideGap = asLeft − asRight`.

### 9.2 왜 Kotlin `GameEvaluator` 를 그대로 쓰지 않는가

`GameEvaluator.evaluate` 는 `Controller` 를 받는다. 정책은 Python/torch 안에 있으므로
Kotlin 이 정책을 부르려면 ONNX 내보내기가 필요하다 — **Phase 7 의 일이다** (PRD §6).
gRPC 로 평가하는 비용은 양 진영 400게임씩에 약 25초다 (PRD §2.6). 아낄 이유가 없다.

대신 **정의가 갈라지지 않게** 한다: 진영별 집계·`combined`·`sideGap` 의 이름과 계산을
`GameEvaluator` 와 동일하게 두고, 무작위 정책 기준선(§2.1)으로 양쪽이 같은 값을 내는지
확인한다 (M3-g).

### 9.3 평가는 별도 서버 프로세스를 쓴다

서버는 **단일 테넌트**다 (`ConfigureReply.session_id`). 평가가 학습 서버에 `Configure` 를
부르면 학습 세션이 무효가 되고 다음 `Step` 이 `FAILED_PRECONDITION` 으로 죽는다.
→ 평가는 자기 UDS 로 서버를 하나 더 띄운다. JVM 하나 더는 16GB 에서 문제되지 않는다.

### 9.4 결정론과 "안 끝나는 게임"

| 모드 | 행동 | 용도 |
|---|---|---|
| `argmax` | 결정론적 | **주 지표** (M3-a). 재실행하면 정확히 같은 수치 (M3-c) |
| `sample` | 확률적 | 보조. 정책의 분산을 본다 |

⚠️ **결정론적 정책 × 거의 결정론적인 FSM = 끝나지 않는 게임이 가능하다.** 잘린 랠리는
득점을 주지 않으므로 (`PikaEnv` 의 truncation) 게임이 영원히 진행될 수 있다.
§2.1 의 측정 3 이 그 현상을 이미 보여줬다.

→ 평가는 게임당 프레임 상한 **60,000** (FSM vs FSM 평균 15,275 의 약 4배) 을 두고,
넘긴 게임은 승/패가 아니라 **`미결(unresolved)` 로 따로 센다.** 조용히 패로 세면 정책이
아니라 상한을 재게 된다. 미결이 1% 를 넘으면 원인을 찾기 전까지 승률을 보고하지 않는다.

### 9.5 진단 축 — boldness 별 승률

`fixedBoldness` 로 FSM 의 boldness 를 0~4 에 고정해 각각 100게임씩 잰다.
난이도 조절이 아니라 **과적합의 모양을 보는 것**이다 — 특정 boldness 에서만 승률이 무너지면
정책이 FSM 의 특정 버릇에 붙은 것이다.

```kotlin
// PikaGame — 추첨은 그대로 두고 덮어쓰기만 한다.
private fun pinBoldness() {
    if (fixedBoldness < 0) return
    physics.player1.computerBoldness = fixedBoldness
    physics.player2.computerBoldness = fixedBoldness
}
```

⚠️ **`rand.next() % 5` 를 건너뛰면 안 된다.** 추첨은 소비되어야 한다. 소비를 없애면 난수
스트림이 어긋나 Phase 1 의 골든과 갈라지고, `fixedBoldness = -1` 일 때와 비교가 불가능해진다.
덮어쓰기는 스트림을 건드리지 않는다.

### 9.6 P3 이 실제로 만든 것

| 파일 | 역할 |
|---|---|
| `evaluate.py` | 게임 경계 검출 · 진영별 집계 · 미결 처리 · boldness 진단 축 · CLI |
| `server_process.py` | 평가 전용 서버 기동 (§9.3). `conftest.py` 도 이것을 쓴다 |
| `scripts/eval-policy.sh` | 체크포인트/기준선 평가 진입점 |
| `RandomBaselineTest.kt` · `BoldnessProbeTest.kt` | Kotlin 쪽 기준선 (§2.1) |

계획에 없었고 만들면서 정한 것 셋:

**1. 표본은 행마다 같은 할당량으로 모은다.** "먼저 끝난 게임부터 N개" 로 세면 **빨리 끝나는
게임이 과대표집된다** — 빠른 행이 여러 판을 넣기 때문이다. 정책이 세질수록 게임이 길어지므로
(PRD §2.6) 이 편향은 학습이 진행될수록 커져서, 승률이 올라가는 것처럼 보이게 만들 수 있다.
그래서 행마다 `games_per_side / 행 수` 를 할당하고 모든 행이 제 몫을 채울 때까지 돌린다.

**2. 진행 중인 게임의 통계는 집계에 넣지 않는다.** 랠리·프레임을 행별로 모아 두었다가
게임이 끝나는 순간 통째로 옮긴다. 스텝마다 바로 더하면 마지막에 끊긴 게임의 절반이 섞여
`GameEvaluator` 의 "게임당 프레임" 과 정의가 갈라진다.

**3. 미결 게임은 행을 죽였다가 되살린다.** 상한을 넘긴 게임은 미결로 세고 그 행을 `dead` 로
표시한다. 그 게임이 실제로 끝나면 `dead` 를 풀고 다음 게임부터 다시 센다. 서버에는 "이 게임을
포기한다" 는 명령이 없으므로 (리셋은 벡터 전체를 되돌린다) 클라이언트가 세지 않는 것이
유일한 방법이다. 영원히 안 끝나는 행이 있어도 `max_steps` 가 **소리 내어** 실패시킨다.

## 10. 프레임 스킵은 지금 하지 않는다

행동 반복(frame skip) 2~4 는 유효 지평을 2~4배 줄이고 RPC 횟수도 그만큼 줄인다.
25 FPS 에서 스킵 2 는 80 ms — 사람의 반응 시간(≈250 ms)보다 짧아 "느려서 지는" 문제도 없다.
**싸고 효과가 큰 손잡이다.** 그런데도 지금 하지 않는 이유:

1. 문제의 정의를 바꾼다. `env` 골든이 깨지고, Track B(Phase 4)와 예산을 맞추려면 두 트랙이
   같은 스킵을 써야 한다 — 즉 Phase 4 의 설계를 지금 결정하게 된다.
2. §3 에서 본 대로 **처리량은 병목이 아니다.** 스킵의 이득은 순수하게 학습 쪽이다.

**도입 결정 규칙**: γ A/B(§5.2) 를 마치고도 학습이 정체하고, 정체의 원인이 "한 프레임짜리
행동으로는 의미 있는 시간 구조를 만들 수 없음" 으로 **메트릭에서 특정될 때** 도입한다.
그때는 `EnvConfig.frameSkip` 을 추가하고 골든을 갱신하며 이유를 커밋 메시지에 적는다.

## 11. 로깅·체크포인트·재현성

- **메트릭**: `runs/<run-id>/metrics.jsonl`, 반복당 한 줄. Phase 5 가 두 트랙을 겹쳐 그릴
  것이므로 스키마를 지금 고정한다: `iter, env_steps, wall_s, lr, ent_coef, shaping_w,
  loss_pi, loss_v, entropy, kl, clipfrac, explained_var, rally_win_rate, term_share{...},
  rally_frames_mean, trunc_rate, action_hist[18]` — **진영별로 따로** (`left.*`, `right.*`).
- **체크포인트**: `runs/<run-id>/ckpt-<env_steps>.pt` — 가중치 + 옵티마이저 + 하이퍼파라미터
  + 시드 + git 커밋 해시. 평가는 체크포인트만 있으면 재현된다 (FR-8).
- **재현성**: `seed` 하나가 (1) torch, (2) numpy, (3) 서버 `base_seed` 를 전부 정한다.
  `torch.set_num_threads(n)` 을 고정하고 `n` 을 체크포인트에 적는다 — 스레드 수가 바뀌면
  리덕션 순서가 바뀌어 M3-d 가 깨진다.
- `runs/` 는 `.gitignore` 에 넣는다 (NFR-6).

### 11.1 P6 이 실제로 만든 것

| 파일 | 역할 |
|---|---|
| `metrics.py` | `JsonlLogger` · `RunDir` · `flatten` · `to_jsonable` · `git_commit` |
| `track_a.py` | `TrackAConfig` · `TrackARunner` · `save_checkpoint` / `load_checkpoint` · CLI |
| `test_metrics.py` | 15개. 서버도 torch 도 띄우지 않는다 |
| `test_track_a.py` | 17개. 구성은 서버 없이, 학습·평가·체크포인트는 실제 서버로 |
| `scripts/train-track-a.sh` | 본 학습 · A/B · 재개 |

**`track_a.py` 에 알고리즘이 한 줄도 없다.** PPO 는 `ppo.py`, 마스킹·GAE 는 `rollout.py`,
스케줄은 `schedules.py`, 평가는 `evaluate.py` 에 있고 러너는 배선과 기록만 한다. P1~P5 가
전부 "환경을 모르는" 모듈로 만들어졌기 때문에 가능했고, 그것이 Phase 4 의 Track B 가
이 파일 하나만 갈아 끼우면 되는 조건이다 (NFR-4).

계획에 없었고 만들면서 정한 것 다섯:

**1. 평가 기록을 `metrics.jsonl` 에 섞지 않는다.** 평가는 수십 반복에 한 번이므로 같은
파일에 두면 **줄마다 스키마가 달라지고**, Phase 5 가 매 줄에서 키 존재를 확인해야 한다.
`evals.jsonl` 로 나눴다.

**2. 비유한 float 는 문자열 `"nan"` · `"inf"` 로 적는다.** `json.dumps` 의 기본 동작인
`NaN` 리터럴은 **유효한 JSON 이 아니고** 다른 언어의 파서가 거부한다. 그렇다고 0 으로
바꾸면 발산했다는 사실 자체가 지워진다 — 그것이야말로 남겨야 할 기록이다.

**3. 진영 합산 지표는 `RolloutMetrics` 안에 둔다.** 러너가 `(좌 + 우) / 2` 로 따로 계산하면
진영별 랠리 **수**가 다를 때(랠리 길이가 다르다) 조용히 다른 값이 된다. 분모는 랠리 수의
합이어야 하고, 그 정의는 한 군데에만 있어야 한다.

**4. ⚠️ `torch.__version__` 은 `str` 이 아니다.** `TorchVersion` 객체이고, 체크포인트에
그대로 담으면 `weights_only=True` 언피클러가 **거부한다**. 즉 학습은 멀쩡히 끝나는데
평가기가 그 체크포인트를 못 읽는다. `test_track_a.py` 의 "평가기가 읽을 수 있는가" 테스트가
잡았다 — 이 테스트가 없었다면 5천만 step 을 돌린 뒤에 알았을 것이다.

**5. Adam 의 `eps` 는 torch 기본값(1e-8)을 쓴다.** PPO 구현체의 관습은 1e-5 지만 §8.1 의
표에 없는 손잡이다. advantage 를 정규화하므로 그래디언트 스케일이 이미 O(1) 이고,
근거 없이 관습을 따르면 P6 의 A/B 가 설명해야 할 축만 는다. `TrackAConfig` 의 필드로
노출해 `config.json` 에 기록되게만 했다.

**바꾸지 않은 것**: H(128) · 엔트로피 계수 · 에폭 · 미니배치 · LR. `tasks.md` P6 은
"필요 시 조정하고 이유를 적는다" 고 했는데 **필요가 없었다** — §8.1 의 첫 설정이 목표를
넘겼다. 조정하지 않은 것도 기록이다.

**본 학습 결과 (5천만 step · γ=0.997 · 시드 3개 · 최종 평가 진영별 400게임)**

| 시드 | 합산 게임승 | 왼쪽 | 오른쪽 | 진영차 | 득점 (좌·우) | 랠리 승률 | trunc(최대) | 미결 | 처리량 |
|---|---|---|---|---|---|---|---|---|---|
| 0 | **1.0000** | 400/400 | 400/400 | .0000 | 6000:0 · 6000:0 | 1.0000 | .0029 | 0 | 136,991 |
| 1 | **1.0000** | 400/400 | 400/400 | .0000 | 6000:0 · 6000:0 | 1.0000 | .0065 | 0 | 140,732 |
| 2 | **1.0000** | 400/400 | 400/400 | .0000 | 6000:0 · 6000:0 | 1.0000 | .0047 | 0 | 140,209 |

시드 3개 × 양 진영 × 400게임 = **2,400게임에서 FSM 이 한 점도 내지 못했다.** 랠리 승률이
1.0000 이라는 것은 argmax 정책이 **모든 랠리를 이겼다**는 뜻이다.

학습 곡선에서 읽을 것 둘:

1. **8.1M 지점에서 왼쪽 진영이 .25 로 급락했다가 회복한다** (진영차 −.75). 학습은 단조롭지
   않고, 그 순간의 체크포인트만 평가했다면 "오른쪽만 학습됐다" 고 오진했을 것이다.
   주기 평가(FR-7)가 아니면 진동 자체가 보이지 않는다.
2. **28.4M 이후 평가 수치가 소수점까지 고정된다.** LR 이 0 으로 선형 감소하면서 정책이
   얼어붙고, 평가가 결정론적(argmax · 고정 `base_seed`)이라 같은 게임이 그대로 재생된다.
   M3-c 가 요구한 성질이 학습 곡선에서 눈으로 확인되는 자리다.

**M3-e 의 확정 수치**: 136,991 ~ 140,732 env-step/s (업데이트 포함, N=512). NFR-1 하한
60,000 의 2.3배이고 P1 의 대리 측정(≈125,000)보다 오히려 높다 — 실제 러너의 GAE·버퍼·
메트릭이 파이썬 루프가 아니라는 확인이다. 5천만 step 이 **6분**이다 (NFR-2 는 60분).

**재현성과 진단 (별도 실행으로 확인)**

| 무엇 | 어떻게 쟀나 | 결과 |
|---|---|---|
| **M3-d** 학습 재현성 | 같은 시드로 20 반복을 두 번 (N=512 실제 규모) | 13개 지표 **불일치 0** — 손실·KL·clipfrac·설명분산·grad norm·진영별 랠리 승률까지 |
| **M3-c** 평가 재현성 | 같은 체크포인트·시드로 두 번 평가 | 리포트 dict 가 `==` 로 **완전히 동일** |
| **FR-8** 체크포인트 독립성 | `scripts/eval-policy.sh` 로 **다른 프로세스**에서 `ckpt-final.pt` 만 평가 | 합산 1.0000 — 러너의 구성 파일 없이 재현된다 |
| **FR-13** boldness 진단 축 | b 를 0~4 로 고정해 각각 진영별 50게임 | **다섯 값 전부 1.0000**, 진영차 .0000 |

boldness 축의 결과가 뜻하는 것: **FSM 의 특정 버릇에 과적합한 흔적이 없다.** b 가 실제로
바꾸는 것은 랠리 길이(FSM 끼리 1,146 → 484 프레임, PRD §2.1)인데, 정책이 그 전 범위에서
똑같이 이긴다. 애초에 b 가 난이도 축이 아니라는 §2.1 의 결론과 일관된다.

## 13. 작업 순서

`tasks.md` 가 체크리스트다. 의존 관계만 여기 적는다.

```
P1 측정·골격 ─┬─▶ P2 진영 분할 ─┬─▶ P3 평가기 ─┐
              │                  │              ├─▶ P6 학습·튜닝 ─▶ P7 보고·이관
              └─▶ P4 롤아웃 ─────┴─▶ P5 PPO ────┘
```

특히 정확해야 하는 것: **P4 → P5**. 롤아웃이 틀린 채로 PPO 를 얹으면 이후의 모든 실패가
알고리즘 탓으로 오진된다.
