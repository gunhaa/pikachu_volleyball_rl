# 문서 골격

세 문서의 기본 형태. 작업 성격에 맞게 덜어내고 더한다.
빈 섹션을 남기지 않는다 — 쓸 내용이 없으면 그 섹션은 없는 게 낫다.

---

## PRD.md

```markdown
# PRD — <작업명> (<상위 로드맵상 위치, 있으면>)

## 1. 개요
무엇을 만드는지 2~3문장. 그리고 **이 작업의 본질이 무엇인지** 한 줄.
(예: "이 작업의 본질은 포팅이 아니라 동치성 증명이다.")

## 2. 배경
이 작업이 기대는 사실들. 조사해서 확인한 것만 쓴다. 근거·출처를 함께.

## 3. 요구사항

### 3.1 기능 요구사항
| ID | 요구사항 |
|---|---|
| FR-1 | ... |

### 3.2 비기능 요구사항
| ID | 요구사항 |
|---|---|
| NFR-1 | ... |

## 4. 완료 조건 (Exit Criteria)
| ID | 지표 | 목표치 |
|---|---|---|
| M1 | 참/거짓으로 판정 가능한 지표 | 구체적 수치 |

타협 불가한 조건이 있으면 여기 명시한다.

## 5. 산출물
파일/디렉터리 트리. 이 작업이 끝났을 때 저장소에 생겨 있어야 할 것.

## 6. 범위 밖 (Out of Scope)
하지 않을 것과 **그것을 어디로 미루는지**.
경계가 애매한 항목은 단서까지 적는다.

## 7. 리스크
| 리스크 | 대응 |
|---|---|
```

## plan.md

```markdown
# plan — <작업명>

`PRD.md` 의 요구사항을 **어떻게** 달성할지에 대한 기술 계획.

## 1. 접근 방식
전체 전략과 그 이유. 특히 순서를 일반적인 것과 다르게 잡았다면 왜인지.

## 2. 검증된 전제
조사로 확인한 사실과 근거. 계획이 성립하는 이유.
(예: 파일명·줄 번호와 함께 인용한 코드, 측정한 수치, 조회한 API 응답)

## 3~N. 설계
판단이 필요했던 지점마다 한 섹션. 각 섹션에는:
- 무엇을 정했는가
- 왜 그렇게 정했는가 (선택지가 있었으면 비교표)
- 실행 구조 — 배관이 어떻게 연결되는지 코드 스케치로
- 함정 — 모르면 밟을 것들

## 마지막. 작업 순서
의존 관계나 우선순위가 있으면 표로. 특별히 정확해야 하는 부분은 표시.
```

**섹션 구성은 작업마다 다르다.** 위는 예시이지 틀이 아니다.
판단이 필요했던 지점이 곧 섹션이 된다.

## tasks.md

```markdown
# tasks — <작업명>

관심사 단위로 Phase 를 나눈다.
(상위 로드맵에도 Phase 가 있다면, 층위가 다름을 한 줄로 밝힌다.)

**의존 관계**
```
P1 ─┬─▶ P2 ─┐
    │        ├─▶ P4 ─▶ P5
    └─▶ P3 ─┘
```
(선형이면 생략)

## P1. <관심사 이름>

> 이 Phase 가 무엇을 만드는지 한 줄. (관련 요구사항 ID)

- [ ] 항목
- [ ] 항목
- [ ] **확인**: 실행 가능한 형태의 검증

## P2. ...

---

## 완료 조건 요약
| ID | 지표 | 목표치 | Phase |
|---|---|---|---|
```

---

## 이관

완료 시:

```
history/<YYYY-MM-DD>-<작업명>/
├── PRD.md
├── plan.md
└── tasks.md
```

날짜는 완료일. 작업명은 kebab-case 로 짧게.
세 문서를 함께 옮겨야 나중에 맥락이 붙어 있다.
